# 功能设计方法：后续功能的使用入口

使用 [ui-design-spec](../skills/ui-design-spec/SKILL.md)，详细规则在[六项交付合同](../skills/ui-design-spec/references/methodology-contract.md)。功能、导航、连续性、审查与执行编排分别承担专业职责，共享同一份规格和任务源。

可在后续任务直接使用：

> 使用 ui-design-spec 的六项设计方法，针对【项目路径】【全产品/具体功能范围】交付菜单与功能对象地图、逐页规格、全部适用子页面和交互面、成功与失败流程、独立设计任务及生成校验。保留既有规格/任务源、菜单、稳定 ID 与批准决定；逐页根据业务问题选布局。先核对现有内容，只补缺口，完整范围不得用几个示范页面代替。视觉与实现按本次明确授权推进。

“继续下一页”时引用原任务、父母版和当前版本即可。规格充足时复用它们；视觉执行由原 Harness 接续。没有母图时可以规划及准备初始页合同；具体父图未批准的继承单元记录依赖缺口。

## 为什么能用于不同业务

- 固定交付的是角色、问题、字段、操作、状态、去向、父依赖和验收，不固定菜单、屏数或布局。
- 列表回答“找到哪个对象”，详情回答“对象当前怎样”，工作台回答“现在处理什么”，向导回答“如何分步完成”，监控回答“发生了什么”；任务要写选择理由与真实内容区。
- 设计单元既可以是整页，也可以是 Tab、抽屉、状态或动作高亮；每项有稳定 ID 与可单独交接的合同。
- 图、文档、流程和任务都引用相同对象；产物存在、候选、获批、实现及运行验收分别报告。

## 校验与证据

新标准包使用 validate_functional_design 的双严格开关，再执行 generate_design_maps 的 --write/--check。生成器只写派生地图，记录 Registry、任务索引、已声明来源的指纹；正文、状态和批准不由生成器编辑。旧格式来源保持兼容。

测试及前向演练记录见[验证记录](../evals/ui-design-spec/methodology-validation.md)。这些检查能发现已声明关系的缺失、漂移和过期；业务范围与视觉质量仍要按[审阅清单](../skills/ui-design-spec/references/review-checklist.md)逐项提供证据。
