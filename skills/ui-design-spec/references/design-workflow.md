# 详细功能设计工作流

本流程将需求展开为可交接的功能、页面、交互和任务合同。接手者应能凭文档明确产品怎么用、每个界面放什么、接下来逐项做什么。标准目录是承载形式，registry.json 是追踪索引；二者都不能替代业务内容的展开。

各步同时满足[六项交付合同](methodology-contract.md)，在现有 Registry 中登记菜单/对象/功能、页面、交互面、转换和设计单元关系。最后生成派生地图并检查过期，不复制任务或审批状态。

## 第一步：建立全产品地图

1. 盘点所有产品端、角色、业务对象、已有文档、导航、页面、接口及任务源。
2. 按业务域分模块，逐项登记已读、部分读取、未读及理由。用户要求全量时，不能只抽取代表页面就宣称覆盖全产品。
3. 写明本轮范围及成熟度：现行事实、确认需求、拟议设计、待确认、已实现、已运行验证分别记录。
4. 确定唯一规格与任务源，保留编号。跨文档冲突逐条定位，不依据日期或文件名自动定胜负。

产物：README 范围与依据、模块覆盖表。出口：范围内每个模块都有来源与处理状态。

## 第二步：先写功能总表，再逐模块写详细规格

总表用于查找，每个模块必须有正文详规或精确引用已有完整详规。不能只交付一张“模块/功能/优先级”表。

每个模块固定回答：

1. **业务目的与核心问题**：谁在什么场景下要得到什么结果？
2. **Scope / Context**：针对哪个组织、项目、活动、会话或其它业务对象？配置数据和运行事实分别属于哪里？
3. **用户与权限**：谁能看、谁能改、何时只读，越权如何提示？
4. **入口与上下游**：从哪里来、完成后到哪里，菜单与页面如何对应？
5. **子功能清单**：每个可观察能力独立描述输入、业务规则、输出、副作用和验收；按业务分解，不按控件凑数。
6. **必须展示的信息**：字段、统计口径、筛选、排序、对象标识和状态；每项说明用户为何需要它。
7. **主要与次要操作**：触发条件、禁用原因、写入时机、重复操作、取消及返回。
8. **业务规则与边界**：版本、幂等、事务、隐私、数据保留、不可逆效果等按实际业务填写。
9. **关键状态与恢复**：正常、空、加载、只读、失败、冲突、结果的实际内容及下一步；不适用给原因。
10. **验收与待确认**：可观察结果、适用平台、证据来源；缺失的业务政策标为待决，不编造阈值或默认策略。

产物：FUNCTION-CATALOG + pages/ 每模块详规。出口：开发能明确“做什么及何时算成功”，无需自行猜测业务规则。

## 第三步：固定信息架构，展开每个页面结构

先定义产品端、全局 Header、导航和对象切换，再定义业务页内部结构。登记导航唯一名称、默认页、选中项、上下文、详情/向导/抽屉归属。页面数量不等于导航数量。

每个主页面或结构显著不同的子页必须有文字布局图或分区表，按阅读顺序注明：

- 顶部：当前位置、对象、标题、状态、页签、核心操作。
- 主体：筛选、摘要、表格/列表/表单/画布等真实业务内容及字段。
- 辅助区：详情、解释、预览、检查清单；是否常驻及何时显示。
- 底部：分页、步骤、提交/返回；哪些固定、哪些随内容滚动。
- 空态/错误：替换哪些区域，保留哪些上下文，主动作变成什么。
- 弹层：真实来源页、打开方式、层级、允许变化区域、关闭/返回后状态与焦点。

示意图可以用文本线框；Mermaid 至少用于导航树和核心流程。未开始视觉设计也必须能根据结构说明搭出正确的信息层级。宽度、主题和视口遵从目标项目的约束。

产物：NAVIGATION、UI-STRUCTURE 与 pages/ 布局。出口：设计者不需要自行发明一级菜单或页面内容分区。

## 第四步：走通每条业务链，写操作转换表

对每条核心用户旅程先画主链，再逐操作补分支：入口 → 输入/选择 → 校验或预览 → 提交 → 结果 → 下一步。业务不需要某阶段时说明，不强加确认或审批。

每次转换写明：当前页面与业务状态、操作者、动作、前置校验、写入/副作用、处理中反馈、成功去向、失败去向、取消/返回、草稿保留或失效规则。

尤其区分：

- 上传成功与业务数据写入成功。
- 预览中的跳过/修复与事务部分提交。
- 点击提交、已接纳、执行中、已确认成功与结果未知。
- 返回/关页面与取消后台任务。
- 设计任务的执行顺序与用户真实操作顺序。

产物：USER-FLOWS Mermaid 旅程 + 操作转换表 + 必要状态机。出口：每个按钮都能追到业务变化和可执行下一步，失败无死路。

## 第五步：用 Registry 固定页面、动作、状态和结果

从前四步提取 Surface，不从截图数量倒推功能。每项登记稳定 ID、父页面、类型、功能、用户问题、入口、必需内容、操作、成功/失败/返回及设计依赖。补足向导步骤、重要异常、结果面和全局交互。

父页面已经定义的外壳、主题与导航通过引用继承；当前条目必须详细描述自身业务差异。不能把“继承父页”当作省略内容的理由。动作可能是就地按钮，不一定是新弹窗；一个 Surface 也不自动等于一张独立图片，遵循目标项目交付约定。

产物：SCREEN-REGISTRY / GLOBAL-SURFACES / registry.json。出口：功能、旅程、界面之间能双向追踪，无孤立页面、无未定义目标。

## 第六步：拆成可以交接的计划任务

按业务依赖安排：补齐规则 → 全局外壳/父页 → 子页与动作 → 异常结果 → 联调与验收。已有任务保留原编号与执行状态，只在唯一任务源补差距。

每项任务除摘要表外，需要**执行说明**（简单任务可内联，不能省字段）：

- 本次只交付什么、对应功能/Surface，哪些相邻内容属于后续任务。
- 输入规格与依赖、目标用户、对象上下文、来源页、当前选中导航。
- 第一屏必须回答的问题、布局类型与内容区、关键业务字段。
- 真实主动作、次动作、禁用条件、成功/失败/返回目标。
- 父页与视觉依赖、固定区域和允许变化区域；无视觉产物时写不适用原因。
- 要覆盖的正常/异常/结果、具体产物路径或命名规则。
- 可观察验收、验证方法、前置任务、责任角色和原任务定位。

禁止仅写“实现人员管理”“完善交互”“优化界面”。设计、实现、验证可以拆为不同任务，但必须共享同一功能和交互合同。

产物：MASTER-PLAN / DESIGN-EXECUTION 任务总表 + 执行说明/精确原任务引用。出口：换一个智能体仍能从当前任务确定输入、边界、交付物与验收，不需要猜测。

## 第七步：按三条主线审阅后交付

1. **功能清单完整**：范围内所有模块都有详细规格；输入、输出、权限、规则、状态和验收已展开。
2. **交互流程清晰**：每个主要操作有明确转换、异常与恢复；图、表和 Registry 一致。
3. **界面结构清晰**：每页内容区、字段、主次操作、导航归属、父页依赖和返回明确。

再核查任务覆盖与依赖、来源冲突及多端要求。先做语义审阅，再运行结构校验。原成果中存在的模糊措辞不得照抄成完成内容，例如“结果依 Registry”需要实际查出目标，查不到就登记缺口。

产物：STATUS 审阅记录 + registry.json。只有 JSON 通过、表格填满或页面齐全，仍不能证明上述三条主线合格。不得把教学示例或历史人工批准直接当作新项目的验收证据。
