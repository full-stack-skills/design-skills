# 接续已有成果的具体示例

## 情境一：已有两份功能文档，补为固定模式

输入：Agent Buddy 已有 PRODUCT_FUNCTION_DESIGN_PLAN.md（F01–F24）与 PRODUCT_SURFACE_REGISTRY.md（B01–B16 等），另有 OpenSpec 任务。用户要求“按固定模式继续整理计划”。

正确接续：

1. 保留 F/B ID、用户确认的双端一致与 Codex 要求、原任务状态。
2. 建来源表，标记两份原文的版本与工作区状态。历史菜单冲突登记为问题，不能只因文档较晚就宣称已获批准。
3. 按七份固定文档承接内容：原功能清单进入 01，导航分区进入 02，八条流程进入 03，页面条目进入 04。
4. 检查每个原条目缺什么。例如原 B06-03 只有简短说明，应补计划字段、返回行为、权限、键盘、过期状态、数据合同与验收；不重复创建 B06-03。
5. 对照正式 tasks.md 映射 2.2、2.6 等条目，写输入、产物、验证和依赖；不要从新文档生成第二套已勾选清单。
6. 创建 delivery.json，审阅其与文档一致，执行校验，失败逐项修复。

完整的 F07 教学切片已放入 [agent-buddy-install-plan](agent-buddy-install-plan/00-scope-and-sources.md)。扩大到全项目时必须加入其它功能和任务，不能用切片通过代表全部通过。

## 情境二：用户新增一个异常分支

输入：“安装前发现目标不可写，要清楚告诉用户怎么处理”。

先在已有 Registry 查到 B06-E02“权限/冲突阻断”，复用该 ID。核对正式权限要求与原任务范围，补以下内容：

| 位置 | 本次增量 |
| --- | --- |
| 来源/功能 | 记录用户新说明；关联 F06/F07，确认预览和写入权限分别校验 |
| B06-E02 | 具体路径、不能写的原因、可选目标或返回动作；不自动提权 |
| 旅程 | 目标选择→预检→阻断→修改目标→重算计划；旧计划不能继续 |
| 任务映射 | 查原任务是否覆盖目标权限；足够则补验收，缺失且已授权才在原源新增 |
| 验证 | 不可写夹具能触发阻断，返回不丢草稿，更换目标后必须新计划 |
| 审阅 | 刷新受影响语义审阅结果；重跑检查器，不沿用历史 pass |

这段示例只说明接续方法，没有修改原 Agent Buddy B06-E02 或批准新产品行为。

## 情境三：另一产品第一次使用技能

输入：“为维修工单系统整理报修、派单、处理、验收和任务计划”。

复用七阶段与八文件合同；角色/对象/导航/功能从维修工单实际资料重新提取。不可带入 Tenant/EventSession、Codex/Runtime、16 个主屏、固定桌面尺寸或原项目审批要求。没有已有任务源时，05-task-plan.md 才作为唯一计划源；已有 OpenSpec 则继续原 change。

## 可交给下一个智能体的接续指令

> 使用 product-interface-spec。先读取当前正式规格、已有功能/Registry 和原任务源，保留 ID、确认记录与任务状态。对照 examples/READING_GUIDE.md 学习输出颗粒度；按固定合同逐阶段补缺，不从头重做。先报告本次输入、覆盖范围与缺口，再完成七份文档和 delivery.json。将所有功能和 Surface 映射到唯一任务源，检查依赖与异常闭环，重新完成语义审阅并运行 validate_delivery.py --require-ready。报告实际结果和未解决项；不得复制示例的产品数据或通过记录。
